# AI Context Contract — UX42.studio

Этот документ определяет, как ИИ-агенты получают контекст, принимают решения и проверяют результат в проекте UX42.studio.

Обязателен для: Claude / CLAUDE.md, Cursor / Cline, Figma Make, новых ИИ-агентов.

Агент не должен «додумывать» продукт, дизайн-систему или архитектуру. Работает по явным правилам и источникам правды.

## 1. Порядок чтения контекста

1. `CLAUDE.md` — продукт, стек, ограничения, приоритеты.
2. `docs/ai-context-contract.md` — этот контракт.
3. `docs/ai-manifesto.md` — продуктовая философия UX42.
4. `Docs/design-system.md` — канон UI (токены, компоненты, лейауты, a11y, анти-паттерны).
5. `Docs/figma-tokens.md` — карта «код ↔ Figma».
6. `Docs/specs/` — спецификация фичи/экрана.
7. `Docs/ui/` — Figma-спеки компонентов.
8. `TEST_PLAN.md` — критерии проверки.

Приоритет при конфликте:
1. Спецификация задачи в `Docs/specs/`
2. Актуальные правила в `Docs/design-system.md`
3. Базовые правила в `Docs/`
4. `CLAUDE.md`
5. Внешние источники

Агент обязан явно сообщить о конфликте.

## 2. Источники правды

| Область | Источник правды | Агент не должен |
|---|---|---|
| Токены | `src/app/globals.css` (`@theme`, `--md-sys-color-*`) | Вводить новые HEX, размеры, радиусы |
| UI-компоненты | `src/components/ui/` (Radix UI + CVA + `cn()`) | Создавать дубли компонентов |
| Layout | `Docs/design-system.md` §4 | Использовать абсолютное позиционирование для базовой раскладки |
| Состояния | `src/lib/theme.ts` | Придумывать собственную модель состояния |
| Навигация | `Docs/specs/`, роуты Next.js App Router | Добавлять экраны вне карты продукта |
| Спецификация фичи | Файл в `Docs/specs/` | Расширять scope без запроса |
| Тесты | `TEST_PLAN.md` | Считать задачу завершённой без проверки критериев |
| Figma ↔ код | `Docs/figma-tokens.md` | Придумывать имена токенов Figma, которых нет в коде |

## 3. Формат задачи

Каждая задача начинается с контракта:

```md
## Task
Что нужно сделать.

## Goal
Какой результат должен быть достигнут.

## Scope
Что входит в задачу.

## Out of scope
Что агент не должен менять.

## Source of truth
Какие файлы, токены, компоненты и спецификации использовать.

## Acceptance criteria
Как проверить, что задача выполнена.
```

Если контекста недостаточно — агент задаёт уточняющие вопросы перед реализацией.


## 4. Правила работы с UI

Агент должен:

- Использовать только утверждённые токены M3 из `src/app/globals.css`.
- Строить layout через flexbox или CSS grid.
- Сохранять иерархию: один главный экран/секция, одна основная action.
- Проектировать состояния: default, hover, focus, active, disabled, loading, empty, error, success.
- Учитывать `prefers-reduced-motion`, светлую/тёмную тему, печать/PDF.
- Проверять поведение на mobile и desktop.
- Использовать семантический HTML и доступные названия.
- Использовать `cn()` и `cva` для вариантов компонентов.
- Иконки только из `lucide-react`.

Агент не должен:

- Хардкодить цвета, шрифты, отступы, радиусы или тени (нет `style={{}}`, нет магических HEX).
- Создавать кастомные компоненты, если есть подходящий из `src/components/ui/` или M3.
- Использовать dropdown при 1–2 вариантах выбора.
- Сочетать FAB с bottom navigation.
- Генерировать placeholder-текст в финальном UI.
- Использовать инлайн-стили (запрещено в CLAUDE.md).

## 5. Правила работы с кодом

Агент должен:

- Сохранять архитектуру и границы слоёв.
- Не переписывать работающий код без необходимости.
- Предпочитать минимальное изменение максимальному рефакторингу.
- Использовать существующие утилиты, хуки, компоненты и типы.
- Добавлять типы для новых данных и публичных API.
- Обновлять документацию при изменении поведения/архитектуры/UI.

Агент не должен:

- Менять глобальную архитектуру в рамках небольшой задачи.
- Удалять/переименовывать токены, компоненты, файлы без подтверждения.
- Вводить новую UI-библиотеку, state-менеджер или зависимость без запроса.
- Оставлять неиспользуемый код, закомментированные блоки, временные решения.

## 6. Работа с Figma и design handoff

Для передачи компонента используется **component contract**, а не картинка.

Минимальный состав контракта:

```md
# Component: Button

## Purpose
Зачем существует компонент.

## Variants
- Filled (default), Tonal, Outlined, Text, Ghost, Destructive

## States
- Default, Hover, Focus-visible, Active, Disabled, Loading

## Tokens
- Color: `--md-sys-color-primary`, `--md-sys-color-error`, и т.д.
- Shape: `--radius-md` (10px)
- Typography: `text-button`
- Spacing: 4px-сетка

## Accessibility
- Имя, роль, состояние; focus-visible:ring-2; зона клика ≥ 44×44px

## Code mapping
- Компонент: `Button` (`src/components/ui/Button.tsx`)
- Props: `variant`, `size`, `disabled`, `loading`
- Импорт: `@/components/ui/Button`

## Do / Don’t
- Do: один filled button на секцию
- Don’t: два equally weighted primary actions
```

Для Figma Make эти же правила упаковываются в `guidelines/`: `overview.md`, `setup.md`, `tokens.md`, `components/`, `patterns/` и `anti-patterns.md`.

## 7. Проверка результата

Перед завершением задачи агент проверяет:

1. Выполнены ли acceptance criteria.
2. Использованы ли только утверждённые токены и компоненты.
3. Работает ли UI в light/dark, mobile/desktop, print.
4. Покрыты ли все необходимые состояния.
5. Не нарушены ли layout, accessibility и performance-правила.
6. Обновлены ли связанные документы.
7. Нет ли новых предупреждений, ошибок сборки или регрессий (`npm run check`).

Отчёт агента:

```md
## Result
Что сделано.

## Files changed
Список изменённых файлов.

## Decisions
Ключевые решения и почему.

## Checks
Что проверено.

## Open questions
Что требует решения пользователя.
```

## 8. Антипаттерны агента

Запрещено:

- Начинать реализацию без источника правды.
- Изобретать новые паттерны, если они уже описаны в docs.
- Смешивать продуктовую задачу, рефакторинг и редизайн в одном изменении.
- Молча расширять scope.
- Выдавать «красивый» результат, который не проходит проверки.
- Ссылаться на устаревшие документы (`Docs/ui-rules.md` упразднён, `Docs/make-export/DESIGN_SYSTEM.md` — legacy).
- Скрывать неопределённости и риски.

## 9. Обновление контракта

Обновляется при изменении стека, архитектуры, источников правды, процесса handoff или режимов UI. Каждое изменение — краткое, конкретное, проверяемое.
